# Semantic Zoom — How It Works

**Version:** 0.3.3 | **Platform:** macOS 12+ | **Stack:** Tauri v2 (Rust + vanilla TypeScript)

---

## 1. Executive Summary

Semantic Zoom is a macOS desktop app that renders markdown documents at three discrete zoom levels — reading view (k=0), section summaries (k=−1), and a document-level story (k=−2). Zoom levels are powered by an embedded `LookupTable` payload inside each `.md` file, authored by AI agents or the companion `semantic-zoom-tools` plugin. The app uses content-addressed IDs, opacity-only transitions, and keyed DOM reconciliation to deliver instant, spatially-anchored zoom without layout thrash.

Phase 1 is complete. Engine B (live LLM synthesis) and System E (HTML export) remain as Phase 2/3 work.

## 2. How the App Works (User-Facing)

### 2.1 Zoom Levels

| Level | Name | What it shows |
|-------|------|---------------|
| k=0 | Reading view | Raw markdown rendered as HTML — paragraphs, code blocks, tables, lists |
| k=−1 | Section view | Plain-English summaries of each section, written by an AI layer |
| k=−2 | Document map | One-screen "story" with Accomplished / Blockers / Next steps |

### 2.2 Navigation

- **Zoom scrubber** — a 3-segment slider at the top of the window with step buttons (±). Each segment maps to a zoom level; snapping triggers the transition.
- **Anchor engine** — zoom transitions don't scroll to pixel positions. They map the currently focused paragraph (or nearest to viewport center) to its semantic parent/child across levels, centering the target node. Zooming out then back in "remembers your place."
- **Caret system** — click to place a caret in any paragraph; arrow keys move between paragraphs. The caret drives the focus mask and anchor resolution.

### 2.3 Focus Mask

When a caret is placed, sibling paragraphs in the same section are spotlit; paragraphs outside the active group are dimmed via an instant `[data-dimmed]` class swap (no CSS transition on the dimming itself — only the opacity crossfade is animated).

### 2.4 Content Map Sidebar

A minimap sidebar shows the document's section structure. Clicking a section heading navigates to it in the viewport.

### 2.5 Document States

The status badge in the toolbar reflects the document's load state:

| State | Badge | Behavior |
|-------|-------|----------|
| `native` | Green | Valid payload found — all 3 zoom levels available |
| `untagged` | Yellow | No payload marker — k=0 only; levels −1/−2 disabled |
| `corrupt` | Red | Payload present but invalid — k=0 + warning badge |
| `empty` | — | No file open — shows empty state with recent files list |

### 2.6 Other Features

- **Content scale** — browser-style zoom (Cmd+= / Cmd+-) for accessibility
- **Native macOS menus** — File > Open, recent files, keyboard shortcuts
- **Hot reload** — file watcher detects external edits and reconciles the DOM without a full rebuild; caret is preserved across reloads via content-addressed ID matching
- **Raw markdown fallback** — untagged/corrupt documents render as plain k=0 markdown

## 3. Architecture Overview

### 3.1 The Ownership Split

The single most important architectural rule:

> **Rust owns disk truth. TypeScript owns view truth.**

| Layer | Owns | Language |
|-------|------|----------|
| Disk | File reading, payload extraction, validation, file watching | Rust |
| View | LookupTable in memory, anchoring, rendering, state management | TypeScript |

### 3.2 IPC Boundary

Exactly **three crossings** between Rust and TypeScript. Adding a fourth requires a flagged decision.

| Crossing | Direction | Purpose |
|----------|-----------|---------|
| `load_document` | TS → Rust | Read file from disk, extract payload, return `LoadResult` (native / untagged / corrupt) |
| `watch_directory` | TS → Rust | Start watching the parent directory of the open file for `*.md` changes |
| `doc://changed` | Rust → TS | Event emitted when a watched file changes (debounced) |

No `@tauri-apps/*` imports exist in `src/engine/**` or `src/ui/**` — enforced by ESLint `no-restricted-imports`.

### 3.3 Key Design Decisions (D1–D9)

| # | Decision | Rationale |
|---|----------|-----------|
| D1 | Opacity-only animation | `filter` is not GPU-composited in WebKit; transitioning it repaints every frame. Opacity is composited and free. |
| D2 | Payload marker: `<!-- semantic-zoom:payload:v1 ... -->` | HTML-comment-safe, invisible in any markdown renderer, versioned. |
| D3 | Engine B is interface + stub in Phase 1 | Phase 1 scope excludes synthesis. |
| D4 | Single RxJS `BehaviorSubject<AppState>` store | Strict rules: `distinctUntilChanged` selectors, no ad-hoc subscriptions in components. |
| D5 | Watch parent directory, not single file | Atomic save patterns (write-to-temp + rename) break single-file watchers. |
| D6 | Content-addressed IDs: `P-<sha256[:8]>-<ordinal>` | Sequential IDs silently re-anchor the caret to different content after mid-document insertion. Hash+ordinal survives insertions. |
| D7 | Keyed per-group DOM reconciliation | Full rebuild of a 5k-line doc blocks the main thread past 250ms. Unchanged groups keep their DOM nodes by identity. |
| D8 | Two-frame zoom mount | One synchronous forced layout of a 10k-paragraph tree can exceed the frame budget. Frame n: append hidden. Frame n+1: measure + scroll + fade. |
| D9 | Remote LLM synthesis (Phase 2) | New Tauri crossings confined to `src/native/**`. API key stored in OS Keychain, never enters webview. |

### 3.4 Data Flow

```
.md file on disk
       │
       ▼
   Rust: extract_payload()     ← byte scan for <!-- semantic-zoom:payload:v1
       │                           ...JSON... -->
       ▼
   Rust: validate() + verify_ids()   ← referential integrity + D6 hash check
       │
       ▼
   load_document command → TypeScript
       │
       ▼
   RxJS store: AppState         ← single BehaviorSubject, components subscribe via selectors
       │
       ▼
   Viewport renders active level  ← keyed reconciliation, opacity crossfade
```

### 4.4 Schema: The LookupTable

The document model is an inverted tree:

```
M1 (k=−2, "The Story")
 ├── S1 (k=−1, section summary)
 │    ├── P1 (k=0, raw paragraph)
 │    └── P2 (k=0, code block)
 └── S2 (k=−1, section summary)
      ├── P3 (k=0, paragraph)
      └── P4 (k=0, list)
```

IDs follow D6: `P-<sha256[:8]>-<ordinal>` for paragraphs, `S-<sha256[:8]>-<ordinal>` for sections, `M1`/`M2` positional for meta. The payload lives at the end of the `.md` file inside `<!-- semantic-zoom:payload:v1 ... -->`.

## 6. The Claude Code Plugin Ecosystem

### 6.1 semantic-zoom-tools (v1.3.0)

**Location:** `tools/semantic-zoom-tools/`

A Claude Code plugin that generates zoom-tagged `.md` files. The core design principle: everything that must be exactly right is a deterministic script; the one genuinely creative task (grouping paragraphs into sections, writing summaries) is left to the model.

#### Pipeline

```
Raw .md file
    │
    ▼
segment.mjs          ← deterministic: unified + remark-parse → AST → byte spans + content-addressed IDs
    │
    ▼
Model (Claude)        ← creative: groups blocks into sections, writes -1/-2 prose → layers.json
    │
    ▼
assemble.mjs          ← deterministic: derives full LookupTable, computes docHash, escapes --> in JSON
    │
    ▼
validate.mjs          ← fast JS mirror of Rust checks (dependency-free, runs on every edit)
    │
    ▼
verify_payload         ← authoritative: calls the app's actual Rust validate() + verify_ids()
```

#### Key Design Choices

- `assemble.mjs` is idempotent — re-running it after editing either the source file or `layers.json` converges to a consistent result
- `validate.mjs` is a standalone reimplementation (fast, dependency-free) for the hook; `verify_payload` is the authoritative gate using the real Rust code
- The `PostToolUse` hook fires on every Write/Edit in a Claude Code session, validating any `.md` file that has a payload marker

#### Installation

```bash
# Per-session
claude --plugin-dir tools/semantic-zoom-tools

# Persistent via local marketplace
claude plugin marketplace add ./.claude-plugin/marketplace.json
claude plugin install semantic-zoom-tools
# Confirm: claude plugin list → look for "Status: ✔ enabled"
```

## 7. Testing and Verification

### 7.1 Test Coverage

~2800 lines of tests across 25 test files covering:

- Rust parser: `validate()`, `verify_ids()`, payload extraction, edge cases (empty files, missing markers, corrupt JSON)
- TypeScript: schema parsing, anchor math, store reducers, selector memoization
- Round-trip: Rust parses `fixtures/zoom_test.md` → TS parses same → structural equality
- Plugin: UTF-16 offset bugs, marker detection, schema drift

### 7.2 Fixtures (Read-Only Acceptance Oracles)

| Fixture | Purpose |
|---------|---------|
| `fixtures/zoom_test.md` | Primary round-trip test document with embedded payload |
| `fixtures/mock-a.md` | Mock document A for multi-file scenarios |
| `fixtures/mock-b.md` | Mock document B for multi-file scenarios |

**Rule:** Fixtures are never regenerated or edited to make a test pass. If a fixture seems wrong, stop and flag.

### 7.3 Verification Layers

| Layer | What it checks | Speed | Authority |
|-------|---------------|-------|-----------|
| `validate.mjs` | Referential integrity, id-to-hash agreement, docHash | Fast, dependency-free | Mirror of Rust logic |
| `verify_payload` (Rust binary) | Calls app's actual `validate()` + `verify_ids()` | Slower (compile + run) | Authoritative — same code the shipping app runs |
| Round-trip test | Rust parses payload → TS parses same → structural equality | CI | Defense against Rust/TS mirror drift |

### 7.4 CI

The round-trip test runs in CI from the moment it exists. When a check fails, the rule is: fix the code, not the check.
