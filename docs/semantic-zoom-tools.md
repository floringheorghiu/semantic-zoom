# semantic-zoom-tools — Plugin Guide

`semantic-zoom-tools` is a Claude Code plugin that generates the `.md` payload this app reads: content at level 0 (your raw paragraphs, untouched), plain-English sections at level −1, and a one-screen story at level −2, all embedded as a single `<!-- semantic-zoom:payload:v1 ... -->` block at the end of the file. This document explains what it does, how it's built, how to install it, and how to actually use it in the situations you'll run into.

## What problem it solves

Every zoom-tagged file needs a `LookupTable` payload matching a strict contract: content-addressed IDs (`P-<sha256(text)[:8]>-<ordinal>`), byte-accurate spans into the pre-payload region, a `docHash` covering exactly those bytes, referential integrity between paragraphs/sections/meta, and careful escaping so the payload's own closing marker can't appear inside a JSON string value by accident. None of that is something you want to type by hand, and none of it is something a language model should be trusted to get right by inference either — a plausible-looking but wrong hash is worse than an obviously missing one, because it passes casual review and only fails once the app tries to load the file (or, worse, passes a naive check and silently corrupts something like caret restoration on hot reload).

The plugin's whole design rests on one split: everything that must be **exactly** right is a deterministic script, never a prompt instruction. The one part that's genuinely a language task — grouping paragraphs into sections and writing the section/story prose — is the only part left to the model.

## Architecture

The pipeline has five pieces, each with one job:

1. **`scripts/segment.mjs`** parses the raw markdown with `unified` + `remark-parse` + `unist-util-visit` — the same parser family this app's own Engine B design specifies — and walks the top-level AST nodes (heading, paragraph, code, list, table, blockquote). Each block gets a byte span into the source and a content-addressed id: `P-<hash8>-<ordinal>`, where the ordinal disambiguates blocks that hash identically (two copies of the same code snippet get `-0` and `-1`, not a collision). It also renders each block's markdown to HTML via `marked`, matching exactly what the app's own DOM builder expects (a `<pre><code>` for code blocks, a `<table>` for tables — no adaptation needed, confirmed by testing).

2. **The model** (a Claude Code session, driven by the `embed-zoom-payload` skill) reads the ordered block list segment.mjs produces and does the one part a script can't: decides which blocks belong in which section, writes a short human title and a 2–5 sentence plain-English body for each section, and writes one story summary of the whole document with three fixed subheadings — Accomplished, Blockers, Next steps. The model never invents, edits, or reorders an id; it only ever copies ids byte-for-byte from what segment.mjs gave it.

3. **`scripts/assemble.mjs`** takes that grouping (`layers.json`) and re-derives the entire `LookupTable` from scratch — it never patches an existing payload in place, which is what keeps it idempotent (re-running it after editing either the source file or `layers.json` converges to a consistent result instead of accreting stale state). It enforces the one structural rule the app's renderer actually needs: a section's paragraphs must be a contiguous run in document order, because the app wraps each section's children in a single DOM element that can't express a gap. It computes `docHash` over the exact bytes that will precede the marker, escapes any literal `-->` inside JSON string values so it can't be mistaken for the marker's own close, and self-checks every id against its own span before writing anything to disk.

4. **`scripts/validate.mjs`** is a standalone, dependency-free reimplementation of the same checks the app's Rust code runs at load time: referential integrity, id-to-content-hash agreement, docHash agreement. It's fast and needs nothing installed, which is exactly why it's what runs automatically on every file edit (see the hook below) — but a reimplementation is still a second copy of logic that could, in principle, drift from what it's mirroring.

5. **`src-tauri/src/bin/verify_payload.rs`**, a small binary in the app's own Rust crate (not part of the shipped GUI app), closes that gap. It calls the app's actual, compiled `validate()` and `verify_ids()` — the exact code `load_document` runs — so a payload this binary accepts is guaranteed acceptable to the real app, not just believed equivalent to it. This exists because of a real incident during this plugin's own development: a bug in `segment.mjs`'s span calculation was completely invisible to the JS mirror (the id and its hash were derived from the same wrong byte range, so they always agreed with each other) and would have been invisible to a second JS reimplementation too. Only reading the actual rendered text — and, ultimately, only the real Rust code — caught it. The skill's last step runs this binary as the authoritative gate, on top of the fast JS check, not instead of it.

Sitting alongside all of this, `hooks/hooks.json` wires `scripts/hook-validate.mjs` to fire on every `Write`/`Edit` tool call in a Claude Code session, anywhere. It's a no-op on anything that isn't a `.md` file and a no-op on a `.md` file with no payload marker; on a file that does have one, it validates and — if that fails — exits with a blocking error message fed back to Claude in the same turn, rather than the drift going unnoticed until the app fails to load the file later. This is what catches the scenario the pipeline can't otherwise prevent: someone (human or another Claude session) hand-editing a tagged file directly instead of going through the pipeline.

## Installation

The plugin lives at `tools/semantic-zoom-tools/` in this repo, structured as a self-contained plugin root with its own `.claude-plugin/plugin.json` — but positioned as a sibling of `src-tauri/` specifically so its final verification step can build and run the app's own Rust binary.

There are two ways to load it, and they trade off differently:

**Per-session, immediate.** Launch Claude Code with `claude --plugin-dir tools/semantic-zoom-tools` from the repo root. Nothing to register, nothing persists — good for a one-off check, but you'd repeat this every session.

**Persistent, via the repo's local marketplace.** A marketplace manifest at `.claude-plugin/marketplace.json` (repo root) declares this plugin with a relative source path. Note the manifest's own location matters: `claude plugin install` resolves a plugin's `source` path relative to the marketplace manifest's *parent* directory, mirroring the same convention a plugin itself uses for its own `plugin.json` — so the manifest has to live at `.claude-plugin/marketplace.json`, not directly at the repo root (a manifest placed one level too shallow resolves every plugin path one directory too high, a failure mode confirmed the hard way during this plugin's own setup). Once it's in the right place:
```
claude plugin marketplace add ./.claude-plugin/marketplace.json
claude plugin install semantic-zoom-tools
```
This registers the plugin so `/reload-plugins` and every future session pick it up automatically. Confirm it actually loaded — not just that the install command reported success — with `claude plugin list`; look for `Status: ✔ enabled` next to `semantic-zoom-tools`.

The skill's final verification step also needs `cargo` on `PATH`, which this repo already requires for the app itself. `scripts/segment.mjs` and `scripts/assemble.mjs` need their own `npm install` run once inside `tools/semantic-zoom-tools/` — `validate.mjs` and the hook are dependency-free and work immediately without it.

## Usage scenarios

**Tagging a file that has never been tagged.** Ask Claude (with the plugin loaded) to embed zoom layers in a specific file. The skill runs `segment.mjs` against it, groups the resulting blocks into sections and writes the −1/−2 prose, hands that to `assemble.mjs`, and runs both verification steps before calling the task done. If you have several candidate files open and don't name one, the skill asks which file rather than guessing.

**Refreshing a payload after the source content changed.** Don't hand-patch the embedded JSON — every byte after an edit shifts every span that comes after it, which is expected behavior, not a bug in the validator. Re-run `segment.mjs` to get fresh ids, carry forward `layers.json`'s section groupings (only the ids that actually changed need updating), and re-run `assemble.mjs` and both verification steps. `assemble.mjs` is safe to re-run on a file that already has a payload — it strips the old one first rather than accreting a second copy.

**A file fails validation and you didn't just build it.** This means something wrote to the file outside the pipeline — almost always a direct hand-edit of the embedded JSON, or an edit to the visible markdown that never went back through `assemble.mjs`. Don't try to reconcile the drift by hand; regenerate from scratch, the same as a refresh.

**Someone edits a tagged file without going through the skill at all.** This is what the `PostToolUse` hook is for. It fires automatically on every `Write`/`Edit`, silently, on every file — no setup needed beyond having the plugin enabled — and only speaks up when it finds a payload-bearing `.md` file whose payload no longer matches its own content. The failure message names the specific mismatch and tells Claude to regenerate through `assemble.mjs`, not to patch the JSON directly.

**The model's grouping output fails the mechanical output contract.** `assemble.mjs` checks the model's `layers.json` against a strict, mechanical contract before it ever touches the file: every referenced id must be real, every section's blocks must be contiguous in document order, every block must land in exactly one section. On the first failure the model gets re-prompted once with the specific violation named; on a second failure the pipeline falls back to shipping the file untagged rather than assembling something that would fail validation anyway.

## A note on the two verification layers

`validate.mjs` and `verify_payload` check the same properties but are not redundant with each other — they exist for different failure modes. `validate.mjs` is fast and dependency-free, which is why it's the one wired into the hook that runs on every single edit; a slow or cargo-dependent check there would make ordinary editing painful. `verify_payload` is slower (it's a real compile-and-run of Rust code) but authoritative, because it runs the exact logic the shipping app runs rather than a hand-maintained mirror of it. Treat a `validate.mjs` pass as "looks right"; treat a `verify_payload` pass as "the app will actually accept this."

## Known limitations

Section groupings must be contiguous in document order — the renderer has no way to express a section whose paragraphs skip around. `segment.mjs` renders HTML via `marked` independently of the `remark` AST used for spans and block kind; both are CommonMark-compliant, so divergence is limited to GFM-extension edge cases like table alignment or strikethrough, not core structure. And because `${CLAUDE_PLUGIN_ROOT}` has a documented reliability gap for some hook events in current Claude Code versions, if the `PostToolUse` hook ever seems to silently stop firing, check whether that environment variable is actually reaching the hook process before assuming the validation logic itself is at fault.
